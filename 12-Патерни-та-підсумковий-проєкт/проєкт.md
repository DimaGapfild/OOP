# Підсумковий проєкт курсу «Об'єктно-орієнтоване програмування»

## Мета

Спроєктувати й реалізувати **консольний (або бібліотечний) застосунок** з
кількох взаємодіючих класів, що демонструє: класи й інкапсуляцію,
успадкування й поліморфізм, абстракцію, композицію, власні винятки,
колекції та принципи SOLID, а також щонайменше **два патерни
проєктування**.

Мова — Python 3 (за домовленістю з викладачем — JavaScript або C++).

## Теми на вибір

### Варіант A. Менеджер завдань (Task Tracker)
Користувачі, проєкти, завдання з пріоритетом і статусом (State),
теги, пошук і фільтрація, історія змін (Command + undo), сповіщення
про прострочені завдання (Observer), експорт у різні формати (Strategy).

### Варіант B. Бібліотека / прокат
Каталог (книги, журнали, диски — ієрархія), читачі, видачі та
повернення, штрафи за прострочення (Strategy), резервування
(Observer), пошук за різними критеріями, звіти (Template Method).

### Варіант C. Банківська система
Рахунки різних типів (успадкування + абстракція), транзакції
(Command), комісії (Decorator/Strategy), ліміти та перевірки
(власні винятки, контракти), виписки, сповіщення (Observer).

### Варіант D. Симулятор (гра або екосистема)
Сутності зі складових-компонентів (композиція), поведінка через
стратегії, події світу (Observer), фабрика створення істот/предметів
(Factory), збереження стану (Memento — за бажанням).

Власну тему можна запропонувати за погодженням.

## Вимоги

### Обов'язкові (на 3 бали)

1. **Не менше 6 класів** із осмисленою відповідальністю.
2. **Класи та інкапсуляція:** приховані дані, `@property` з валідацією,
   `__str__`/`__repr__`.
3. **Успадкування та поліморфізм:** щонайменше одна ієрархія з 3+ класів;
   клієнтський код працює через базовий тип.
4. **Абстракція:** щонайменше один абстрактний клас або інтерфейс.
5. **Власні винятки:** базовий виняток модуля й щонайменше два нащадки.
6. **Тести:** не менше 10 перевірок (`assert` або `unittest`/`pytest`).
7. **Діаграма класів UML** (Mermaid) у файлі `README.md` проєкту.
8. **README:** опис, запуск, приклад роботи, список патернів і принципів,
   які застосовано, та де саме.

### Додаткові (на 4–5 балів)

9. **Патерни:** щонайменше 2 для 4 балів, 3+ для 5 балів — із
   обґрунтуванням, навіщо кожен.
10. **SOLID:** залежності передаються ззовні (DI); продемонструйте
    **розширення без змін** існуючого коду.
11. **Композиція над успадкуванням** там, де зв'язок не «є».
12. **Колекції та ітератори:** власна колекція (`__iter__`, `__len__`,
    `__getitem__`) або генератор.
13. **dataclass / Enum** для даних і станів.
14. **Діаграма послідовності** для головного сценарію.
15. Тести на **фейках** (замість реальних файлів/мережі).

## Структура репозиторію

```
project/
├── README.md              # опис, UML, патерни, запуск
├── src/
│   ├── models.py          # сутності
│   ├── services.py        # бізнес-логіка
│   ├── errors.py          # власні винятки
│   └── ...
├── tests/
│   └── test_*.py
└── main.py                # точка входу / демонстрація
```

## Етапи роботи

| Етап | Що робимо | Результат |
|------|-----------|-----------|
| 1. Аналіз | перелік сутностей, дій, правил | список вимог (user stories) |
| 2. Проєктування | діаграма класів, розподіл відповідальностей | UML у README |
| 3. Каркас | порожні класи, інтерфейси, винятки | код, що імпортується |
| 4. Реалізація | по одному класу + тести | зелені тести |
| 5. Інтеграція | `main.py` із повним сценарієм | демонстрація |
| 6. Рефакторинг | перевірка на SOLID, усунення дублювання | чистий код |
| 7. Захист | показ, відповіді на питання | оцінка |

## Рубрика оцінювання

| Критерій | Макс. | Опис |
|----------|-------|------|
| Проєктування (UML, відповідальності) | 2 | діаграма відповідає коду; класи мають одну причину для зміни |
| ООП-принципи | 3 | інкапсуляція, успадкування/поліморфізм, абстракція, композиція |
| Патерни та SOLID | 2 | доречність, ознаки розширення без змін |
| Якість коду й обробка помилок | 1.5 | читабельність, docstring, винятки замість «магічних» значень |
| Тести | 1 | покриття основних сценаріїв і граничних випадків |
| Документація та захист | 0.5 | README, відповіді на питання |
| **Разом** | **10** | |

Переведення: 9–10 → 5; 7–8.9 → 4; 5–6.9 → 3; менше 5 — доопрацювання.

## Типові помилки

- «Божественний клас», що робить усе (порушення S);
- наслідування заради повторного використання коду (замість композиції);
- `isinstance` по всьому коду замість поліморфізму;
- залежність від конкретних класів: `self.db = MySqlDb()` усередині сервісу;
- глобальний стан (Singleton) у кожному куті;
- винятки `Exception("щось пішло не так")` без власних типів;
- діаграма, що не відповідає коду.

## Контрольні питання до захисту

1. Які сутності ви виділили і чому саме такі межі класів?
2. Де у проєкті поліморфізм і що б сталося без нього?
3. Який принцип SOLID найлегше порушити у вашому проєкті й як ви цього уникли?
4. Покажіть, як додати нову можливість (новий тип/правило) **без правок** існуючих класів.
5. Чому тут композиція, а не успадкування (або навпаки)?
6. Як ви тестували клас, що залежить від зовнішньої системи?
