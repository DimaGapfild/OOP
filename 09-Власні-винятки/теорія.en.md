# Chapter 9. Custom Exceptions and Contracts

## 9.1 Why Custom Exceptions

The built-in `ValueError`, `KeyError`, etc. describe a **technical** error.
A custom exception describes an error of the **problem domain**:
`InsufficientFundsError`, `UserNotFoundError`. The benefit is that code that
catches errors reads like a description of business rules rather than of technicalities.

**Python**

```python
class BankError(Exception):
    """The base exception of the banking module."""

class InsufficientFundsError(BankError):
    def __init__(self, balance: float, needed: float):
        super().__init__(f"insufficient funds: have {balance}, need {needed}")
        self.balance = balance          # data about the error — attributes
        self.needed = needed
```

**JavaScript**

```js
/** The base exception of the banking module. */
class BankError extends Error {
    constructor(message, options) {
        super(message, options);
        this.name = this.constructor.name;
    }
}

class InsufficientFundsError extends BankError {
    constructor(balance, needed) {
        super(`insufficient funds: have ${balance}, need ${needed}`);
        this.balance = balance;         // data about the error — fields
        this.needed = needed;
    }
}
```

**C++**

```cpp
#include <stdexcept>
#include <string>

// The base exception of the banking module.
class BankError : public std::runtime_error {
public:
    using std::runtime_error::runtime_error;
};

class InsufficientFundsError : public BankError {
public:
    InsufficientFundsError(double balance, double needed)
        : BankError("insufficient funds: have " + std::to_string(balance) +
                    ", need " + std::to_string(needed)),
          balance(balance), needed(needed) {}

    const double balance;               // data about the error — fields
    const double needed;
};
```

Rules:

- inherit from `Exception` (not from `BaseException`);
- the name ends with `Error` (for errors);
- create a module **base** exception — users can then catch everything with one `except BankError`;
- store useful data as attributes, not only as message text.

## 9.2 An Exception Hierarchy

```
Exception
└── BankError
    ├── InsufficientFundsError
    └── AccountClosedError
```

**Python**

```python
try:
    account.withdraw(500)
except InsufficientFundsError as e:      # the specific error — first
    print(e.needed - e.balance)
except BankError:                        # the other banking errors — after
    ...
```

**JavaScript** — there is only one `catch`; the type is checked with `instanceof`:

```js
try {
    account.withdraw(500);
} catch (e) {
    if (e instanceof InsufficientFundsError) {   // the specific error — first
        console.log(e.needed - e.balance);
    } else if (e instanceof BankError) {         // the other banking errors — after
        // ...
    } else {
        throw e;                                 // foreign errors — pass them on
    }
}
```

**C++** — exceptions are caught **by const reference**:

```cpp
try {
    account.withdraw(500);
} catch (const InsufficientFundsError& e) {      // the specific error — first
    std::cout << e.needed - e.balance << "\n";
} catch (const BankError& e) {                   // the other banking errors — after
    // ...
}
```

The order of `except` blocks matters: **specific first, then general**.

> **Language difference: what can be thrown and how to catch it.**
>
> - **Python** — only objects derived from `BaseException`
>   (`raise "text"` gives a `TypeError`).
> - **JavaScript** — **anything**: `throw "error"` or `throw 42` are
>   allowed, but then there is no stack trace and no `instanceof`. Always
>   throw `Error` or its subclasses.
> - **C++** — also anything (`throw 42;`), but the convention is to throw
>   subclasses of `std::exception`. Catch **by reference**:
>   `catch (BankError e)` (by value) **slices** `InsufficientFundsError`
>   down to `BankError` — overridden virtual methods and extra fields are lost.
>
> An uncaught exception: Python and Node.js print a traceback and exit;
> C++ calls `std::terminate` (an abnormal exit, destructors may not run).

## 9.3 Catching and Handling Exceptions

**Python**

```python
try:
    value = int(text)               # the risky operation (as little code as possible!)
except ValueError:
    value = 0                       # handling
else:
    log("parsed")                   # only if NO exception occurred
finally:
    cleanup()                       # ALWAYS: on error and on return
```

**JavaScript** — there is no `else` block; that code goes at the end of `try`:

```js
let value;
try {
    value = Number.parseInt(text, 10);
    if (Number.isNaN(value)) throw new RangeError("not a number");
    log("parsed");
} catch {
    value = 0;                      // handling
} finally {
    cleanup();                      // ALWAYS
}
```

**C++** — there is no `finally`: cleanup is done by **destructors** (RAII):

```cpp
int value;
{
    Cleanup guard;                  // the destructor runs ALWAYS
    try {
        value = std::stoi(text);
        log("parsed");
    } catch (const std::invalid_argument&) {
        value = 0;                  // handling
    }
}                                   // here guard.~Cleanup() → cleanup()
```

## 9.4 Exception Chaining

When turning a technical error into a domain one, **do not lose the cause**:

**Python**

```python
try:
    port = int(config["port"])
except KeyError as e:
    raise ConfigError("port is not specified") from e      # e -> __cause__
```

**JavaScript**

```js
const port = config.port;
if (port === undefined) {
    throw new ConfigError("port is not specified", { cause: new Error("no key") });
}
// the cause is available as err.cause
```

**C++**

```cpp
try {
    int port = std::stoi(config.at("port"));
} catch (const std::out_of_range&) {
    std::throw_with_nested(ConfigError("port is not specified"));
}
// the cause is retrieved with std::rethrow_if_nested(e)
```

`raise ... from e` stores the original error in `__cause__`;
`raise ... from None` hides it deliberately. Without `from`, the exception
being handled at that moment ends up in `__context__`.

## 9.5 Guaranteed Resource Release

They guarantee that a resource is released — the analogue of RAII in C++.

**Python**

```python
class Transaction:
    def __init__(self, db): self.db = db
    def __enter__(self):
        self.snapshot = dict(self.db.data)
        return self
    def __exit__(self, exc_type, exc, tb):
        if exc_type is not None:
            self.db.data = self.snapshot     # rollback
        return False                         # False/None — the exception propagates
```

**JavaScript** — `try/finally` (or `using` with `[Symbol.dispose]` in newer engines):

```js
function inTransaction(db, action) {
    const snapshot = { ...db.data };
    try {
        return action();
    } catch (e) {
        db.data = snapshot;            // rollback
        throw e;                       // the exception propagates
    }
}
```

**C++** — RAII: the destructor rolls back the changes unless `commit()` was called:

```cpp
class Transaction {
public:
    explicit Transaction(Db& db) : db(db), snapshot(db.data) {}

    ~Transaction() {
        if (!committed) db.data = snapshot;   // rollback
    }

    void commit() { committed = true; }

private:
    Db& db;
    std::map<std::string, int> snapshot;
    bool committed = false;
};
```

The short form:

**Python**

```python
from contextlib import contextmanager

@contextmanager
def opened(name, log):
    log.append(f"open {name}")
    try:
        yield name
    finally:
        log.append(f"close {name}")
```

**JavaScript** — a function that takes the "body" as a callback:

```js
function opened(name, log, body) {
    log.push(`open ${name}`);
    try {
        return body(name);
    } finally {
        log.push(`close ${name}`);
    }
}
```

**C++**

```cpp
class Opened {
public:
    Opened(std::string name, std::vector<std::string>& log)
        : name(name), log(log) { log.push_back("open " + name); }
    ~Opened() { log.push_back("close " + name); }

private:
    std::string name;
    std::vector<std::string>& log;
};
```

## 9.6 Contracts: Design by Contract

A method's **contract** consists of:

| Element | Question | Who is responsible |
|---------|----------|--------------------|
| **Precondition** | what must be true **before** the call | the caller |
| **Postcondition** | what the method **guarantees** after it runs | the method |
| **Invariant** | what is **always** true for the object between calls | the class |

A precondition violation is the **caller's** fault (we raise `ValueError`/
`ContractError`). A postcondition or invariant violation is a **bug
in the code itself** (`assert`, `InvariantError`).

**Python**

```python
def requires(pred, msg):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            if not pred(*a, **kw):
                raise ContractError(msg)
            return fn(*a, **kw)
        return wrapper
    return deco
```

**JavaScript** — a higher-order function instead of a decorator:

```js
function requires(pred, msg, fn) {
    return function (...args) {
        if (!pred(...args)) throw new ContractError(msg);
        return fn.apply(this, args);
    };
}
```

**C++** — the precondition is checked at the start of the method;
`assert` (from `<cassert>`) is disabled by the `NDEBUG` macro, just
like `python -O`:

```cpp
#include <cassert>

void withdraw(double amount) {
    if (amount <= 0) {                         // precondition
        throw std::invalid_argument("amount must be > 0");
    }
    balance -= amount;
    assert(balance >= 0);                      // invariant (an internal assumption)
}
```

`assert` is disabled by the `python -O` flag, so **do not use
it to validate user input** — only for internal
assumptions.

## 9.7 Exception or Result Value?

| Approach | When |
|----------|------|
| Exception | the error is **exceptional**, the calling level cannot handle it |
| `None` / return code | the absence of a result is a normal situation |
| `Result` (ok / err) | the error is an **expected** outcome; we want to force it to be handled |

**Python**

```python
r = safe_div(10, 0)                  # a Result, not an exception
value = r.unwrap_or(0)
```

**JavaScript**

```js
const r = safeDiv(10, 0);            // { ok: false, error: "..." }
const value = r.ok ? r.value : 0;
```

**C++** — `std::optional` or C++23 `std::expected`:

```cpp
#include <expected>

std::expected<double, std::string> safeDiv(double a, double b) {
    if (b == 0) return std::unexpected("division by zero");
    return a / b;
}

double value = safeDiv(10, 0).value_or(0);
```

## 9.9 Comparison with Other Languages

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Base class | `Exception` | `Error` | `std::exception` |
| Chaining | `raise X from e` | `new Error(msg, { cause: e })` | `std::throw_with_nested` |
| `finally` | yes | yes | **none** — RAII (destructors) |
| Context manager | `with` | `try/finally`, `using` (new) | RAII |
| Exception specification | none | none | `noexcept` |
