# Chapter 5. Inheritance

## 5.1 The Idea

**Inheritance** is creating a new class (the **child**, subclass) based on
an existing one (the **parent**, base class): the child receives all of the parent's
attributes and methods and can add its own or change the inherited ones.

The relationship is "**is a kind of**" (is-a): a dog *is* an animal, a student *is* a person.

**Python**

```python
class Animal:
    def __init__(self, name: str):
        self.name = name

    def speak(self) -> str:
        return "..."

    def intro(self) -> str:
        return f"{self.name} says: {self.speak()}"


class Dog(Animal):                 # Dog inherits Animal
    def speak(self) -> str:        # override
        return "Woof!"


class Cat(Animal):
    def speak(self) -> str:
        return "Meow!"


print(Dog("Rex").intro())          # Rex says: Woof!
```

**JavaScript**

```js
class Animal {
    constructor(name) {
        this.name = name;
    }

    speak() {
        return "...";
    }

    intro() {
        return `${this.name} says: ${this.speak()}`;
    }
}

class Dog extends Animal {         // Dog inherits Animal
    speak() {                      // override
        return "Woof!";
    }
}

class Cat extends Animal {
    speak() {
        return "Meow!";
    }
}

console.log(new Dog("Rex").intro());    // Rex says: Woof!
```

**C++** — a method that may be overridden is marked `virtual`:

```cpp
#include <iostream>
#include <string>

class Animal {
public:
    explicit Animal(std::string name) : name(name) {}
    virtual ~Animal() = default;

    virtual std::string speak() const {
        return "...";
    }

    std::string intro() const {
        return name + " says: " + speak();
    }

protected:
    std::string name;
};

class Dog : public Animal {        // Dog inherits Animal
public:
    using Animal::Animal;          // inherit the constructor

    std::string speak() const override {
        return "Woof!";
    }
};

class Cat : public Animal {
public:
    using Animal::Animal;

    std::string speak() const override {
        return "Meow!";
    }
};

int main() {
    std::cout << Dog("Rex").intro() << "\n";    // Rex says: Woof!
}
```

Terminology:

| Term | Meaning |
|------|---------|
| base class, parent, superclass | `Animal` |
| derived class, child, subclass | `Dog` |
| override | the child changes the parent's method |
| extension | the child adds new attributes/methods |

> **Language difference: `virtual` in C++.** In Python and JavaScript
> **any** method can be overridden, and the call always picks the
> version by the object's real type. In C++ this holds only for methods
> marked `virtual`:
>
> ```cpp
> Dog d("Rex");
> Animal& a = d;
> a.speak();               // with virtual — "Woof!"; WITHOUT virtual — "..." (Animal's version)
> ```
>
> The second C++ trap is **slicing**: assigning a subclass object to a
> base-type **value** variable copies only the parent part:
>
> ```cpp
> Animal copy = d;         // slicing: only the Animal part of Dog is left
> copy.speak();            // "..." — even with virtual
> ```
>
> That is why polymorphic objects in C++ are passed by reference
> (`Animal&`) or by pointer (`unique_ptr<Animal>`). In Python and JS
> variables are always references, so slicing never happens there.

## 5.2 Calling the Parent

If a child has its own `__init__`, it **must** call the parent's
constructor, otherwise the parent's attributes will not be created.

**Python**

```python
class Employee:
    def __init__(self, name, salary):
        self.name, self.salary = name, salary

    def pay(self):
        return self.salary


class Manager(Employee):
    def __init__(self, name, salary, bonus):
        super().__init__(name, salary)     # initialize the parent part
        self.bonus = bonus

    def pay(self):
        return super().pay() + self.bonus  # extension, not replacement
```

**JavaScript** — `super(...)` in the constructor is mandatory and must
come **before** the first use of `this`:

```js
class Employee {
    constructor(name, salary) {
        [this.name, this.salary] = [name, salary];
    }

    pay() {
        return this.salary;
    }
}

class Manager extends Employee {
    constructor(name, salary, bonus) {
        super(name, salary);               // initialize the parent part
        this.bonus = bonus;
    }

    pay() {
        return super.pay() + this.bonus;   // extension, not replacement
    }
}
```

**C++** — the parent constructor is called in the initializer list:

```cpp
class Employee {
public:
    Employee(std::string name, double salary) : name(name), salary(salary) {}
    virtual ~Employee() = default;

    virtual double pay() const {
        return salary;
    }

protected:
    std::string name;
    double salary;
};

class Manager : public Employee {
public:
    Manager(std::string name, double salary, double bonus)
        : Employee(name, salary), bonus(bonus) {}   // the parent part

    double pay() const override {
        return Employee::pay() + bonus;             // extension, not replacement
    }

private:
    double bonus;
};
```

`super().method()` is the best way to **reuse** the parent's logic.

> **Language difference: forgetting to call the parent constructor.**
>
> | Python | JavaScript | C++ |
> |---|---|---|
> | no error; the parent's attributes simply do not exist — `AttributeError` only when `self.name` is accessed | `ReferenceError` **right when the object is created**: "Must call super constructor" | the compiler calls the parent's parameterless constructor itself; if there is none — a **compile error** |
>
> Python is the least strict here: the object is created "half-ready",
> and the error appears later and in a different place.

## 5.3 Checking Types and Class Hierarchy

**Python**

```python
d = Dog("Rex")
isinstance(d, Dog)        # True
isinstance(d, Animal)     # True  — a child "is" the parent
isinstance(d, Cat)        # False
issubclass(Dog, Animal)   # True
type(d) is Animal         # False — the exact type
```

**JavaScript**

```js
const d = new Dog("Rex");
d instanceof Dog;                       // true
d instanceof Animal;                    // true  — a child "is" the parent
d instanceof Cat;                       // false
Dog.prototype instanceof Animal;        // true  — like issubclass
d.constructor === Animal;               // false — the exact type
```

**C++**

```cpp
#include <type_traits>

Animal* a = new Dog("Rex");
dynamic_cast<Dog*>(a) != nullptr;       // true
dynamic_cast<Cat*>(a) != nullptr;       // false
std::is_base_of_v<Animal, Dog>;         // true  — like issubclass (compile time)
typeid(*a) == typeid(Animal);           // false — the exact type
delete a;
```

Check with `isinstance`, not `type(x) == ...`: that way subclasses work too.

## 5.4 The Liskov Substitution Principle (LSP)

A child object must be **substitutable without problems** for the parent.
A child must not strengthen the requirements on input data or break
the parent's guarantees. The classic counter-example: `Square(Rectangle)`, where
changing the width changes the height — code that works with a rectangle
breaks. If the "is-a" relationship is artificial, use composition
(chapter 8).

## 5.5 Multiple Inheritance and the MRO

Python allows several parents:

**Python**

```python
class Flyer:
    def move(self): return "flies"

class Swimmer:
    def move(self): return "swims"

class Duck(Flyer, Swimmer):
    pass

Duck().move()             # "flies" — taken from the first parent
print(Duck.__mro__)       # (Duck, Flyer, Swimmer, object)
```

**JavaScript** — there is no multiple class inheritance, so mixins are
written as functions that return a class:

```js
const Flyer = (Base) => class extends Base {
    move() { return "flies"; }
};
const Swimmer = (Base) => class extends Base {
    move() { return "swims"; }
};

class Duck extends Flyer(Swimmer(Object)) {}

new Duck().move();       // "flies" — the nearest one in the prototype chain
```

**C++** — multiple inheritance exists, but an ambiguity must be
resolved **explicitly**, otherwise it is a compile error:

```cpp
struct Flyer   { std::string move() const { return "flies"; } };
struct Swimmer { std::string move() const { return "swims"; } };

struct Duck : Flyer, Swimmer {
    using Flyer::move;   // pick the version explicitly
};

Duck().move();           // "flies"
```

For the "diamond" C++ uses `virtual` inheritance
(`class B : virtual public A`) so that there is only one `A` part.

The **MRO** (Method Resolution Order) is the order in which methods are looked up; it is computed
by the C3 algorithm. "Diamond" inheritance is resolved because each
class appears in the MRO once. `super()` follows the **MRO**, not simply
"to the parent".

## 5.6 Mixins

A **mixin** is a small class with one narrow extra capability that is
"mixed into" other classes (its instances are not created on their own):

**Python**

```python
class ReprMixin:
    def __repr__(self):
        fields = ", ".join(f"{k}={v!r}" for k, v in vars(self).items())
        return f"{type(self).__name__}({fields})"


class Point(ReprMixin):
    def __init__(self, x, y):
        self.x, self.y = x, y
```

**JavaScript** — a mixin as a function over a class:

```js
const ReprMixin = (Base) => class extends Base {
    toString() {
        const fields = Object.entries(this)
            .map(([k, v]) => `${k}=${JSON.stringify(v)}`)
            .join(", ");
        return `${this.constructor.name}(${fields})`;
    }
};

class Point extends ReprMixin(Object) {
    constructor(x, y) {
        super();
        [this.x, this.y] = [x, y];
    }
}
```

**C++** — mixins are built with the **CRTP** template (the subclass
passes itself as the template parameter):

```cpp
#include <sstream>

template <typename Derived>
struct PrintMixin {
    std::string toString() const {
        std::ostringstream out;
        static_cast<const Derived&>(*this).print(out);
        return out.str();
    }
};

struct Point : PrintMixin<Point> {
    int x, y;
    Point(int x, int y) : x(x), y(y) {}
    void print(std::ostream& out) const {
        out << "Point(x=" << x << ", y=" << y << ")";
    }
};
```

## 5.7 Inheritance or Composition?

| Inheritance | Composition |
|-------------|-------------|
| "is a" (is-a) | "has a" (has-a) |
| rigid dependence on the parent | flexible replacement of parts |
| convenient for small, natural hierarchies | better than deep hierarchies |

Rule: **prefer composition**; use inheritance when
the "is-a" relationship is truly natural.

## 5.8 Comparison with Other Languages

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Syntax | `class B(A):` | `class B extends A {` | `class B : public A {` |
| Calling the parent | `super().f()` | `super.f()` | `A::f()` |
| Parent constructor | `super().__init__(..)` | `super(..)` (first!) | initializer list `: A(..)` |
| Multiple | yes, MRO | no (mixin functions) | yes, `virtual` for the diamond |
| Type check | `isinstance` | `instanceof` | `dynamic_cast` |
