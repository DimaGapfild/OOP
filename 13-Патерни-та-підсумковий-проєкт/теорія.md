# Розділ 13. Патерни проєктування та підсумковий проєкт

## 13.1 Що таке патерн проєктування

**Патерн** — типовий перевірений спосіб розв'язання типової проблеми
проєктування. Це не готовий код, а **шаблон**, який адаптують до задачі.
Каталог «Банди чотирьох» (GoF, 1994) налічує 23 патерни трьох груп:

| Група | Питання | Приклади |
|-------|---------|----------|
| **Породжувальні** | як створювати об'єкти | Singleton, Factory, Builder |
| **Структурні** | як складати об'єкти в структури | Adapter, Decorator, Composite |
| **Поведінкові** | як об'єкти взаємодіють | Strategy, Observer, Command, State |

Патерн = **назва + проблема + розв'язок + наслідки**. Користь від назви:
фраза «тут Observer» передає цілий дизайн у двох словах.

> Не застосовуйте патерн «заради патерну». Спершу — проста реалізація;
> патерн з'являється, коли виникає **реальна біль** (дублювання,
> жорсткий зв'язок, неможливість розширити).

## 13.2 Singleton (одинак)

Гарантує **єдиний екземпляр** класу й глобальну точку доступу.

```python
class AppConfig:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.values = {}
        return cls._instance

AppConfig() is AppConfig()      # True
```

Застереження: це **глобальний стан** — ускладнює тестування. Часто краще
передати єдиний об'єкт через конструктор (Dependency Injection, розділ 8).
У Python «одинаком» часто слугує просто **модуль**.

## 13.3 Factory (фабрика)

Інкапсулює створення об'єктів: клієнт просить «створи circle», не знаючи
конкретного класу.

```python
class ShapeFactory:
    _registry = {}

    @classmethod
    def register(cls, kind, creator): cls._registry[kind] = creator

    @classmethod
    def create(cls, kind, *args):
        return cls._registry[kind](*args)
```

Реєстр робить фабрику **відкритою для розширення** (принцип O): новий
вид — `register(...)`, без правок самої фабрики.

## 13.4 Builder (будівельник)

Покроково збирає складний об'єкт; відокремлює **конструювання** від
**подання**. Корисний, коли в конструктора десяток необов'язкових
параметрів.

```python
pizza = (PizzaBuilder().size(30).sauce("томатний")
         .topping("сир").topping("гриби").build())
```

`build()` перевіряє обов'язкові параметри й повертає (часто незмінний)
готовий об'єкт.

## 13.5 Adapter (адаптер)

Перетворює **інтерфейс одного класу в інтерфейс, якого очікує клієнт**.
Використовується для інтеграції старого або стороннього коду.

```python
class FahrenheitSensorAdapter(TemperatureSensor):
    def __init__(self, legacy): self._legacy = legacy
    def celsius(self): return (self._legacy.read_fahrenheit() - 32) * 5 / 9
```

## 13.6 Decorator (декоратор)

Динамічно **додає поведінку** об'єктові, **обгортаючи** його
об'єктом із тим самим інтерфейсом. Альтернатива успадкуванню без
«вибуху» підкласів.

```python
coffee = Caramel(Milk(Espresso()))      # вкладені обгортки
coffee.cost()                           # сума всіх шарів
```

(Не плутати з синтаксисом Python `@decorator` для функцій — це споріднена,
але інша ідея.)

## 13.7 Strategy (стратегія)

Сімейство взаємозамінних алгоритмів за **спільним інтерфейсом**; клієнт
вибирає й міняє їх під час виконання (розділ 11, принцип O).

```python
sorter = Sorter(MergeSort())
sorter.strategy = BubbleSort()          # заміна «на льоту»
```

## 13.8 Observer (спостерігач)

Об'єкт-**суб'єкт** сповіщає список **підписників** про зміну стану,
не знаючи їхніх класів — слабкий зв'язок. Основа подій, GUI,
реактивного програмування.

```python
stock.attach(logger); stock.attach(alert)
stock.set_price(105)           # усі підписники отримують сповіщення
```

Типові ризики: забуті відписки (витоки пам'яті), порядок сповіщень,
каскадні оновлення.

## 13.9 Command (команда)

Інкапсулює **запит як об'єкт**: можна поставити в чергу, залогувати
та **скасувати**.

```python
class Command(ABC):
    def execute(self): ...
    def undo(self): ...

history.execute(InsertCommand(editor, "Привіт"))
history.undo()
```

## 13.10 State (стан)

Об'єкт змінює поведінку при зміні внутрішнього стану: замість величезних
`if status == ...` кожен стан — **окремий клас**, що знає допустимі
переходи.

```python
class Paid(OrderState):
    def ship(self, order): order.state = Shipped()
    def pay(self, order):  raise InvalidTransition("вже оплачено")
```

## 13.11 Патерни та принципи

| Патерн | Реалізує принцип |
|--------|------------------|
| Strategy, Decorator, Factory (реєстр) | **O** — розширення без змін |
| Adapter | **D**, **I** — клієнт залежить від свого інтерфейсу |
| Observer | **D** — слабкий зв'язок суб'єкта й підписників |
| Builder | **S** — окремий об'єкт для конструювання |
| State, Command | **S**, **O** — кожен варіант поведінки в окремому класі |

## 13.12 Підсумковий проєкт

Фінальне завдання курсу — невеликий **застосунок із кількох
взаємодіючих класів**, що демонструє весь вивчений матеріал. Повний
опис, варіанти тем, вимоги й рубрику оцінювання див. у файлі
`проєкт.md`.

## 13.13 Версіонування продукту

Коли проєкт має користувачів (навіть одного), їм потрібно знати, **чи
безпечно оновлюватися**. Це повідомляє номер версії. Стандарт —
**семантичне версіонування** (SemVer, semver.org): `MAJOR.MINOR.PATCH`,
наприклад `2.4.1`.

| Що змінилось | Яку цифру підвищити | Приклад з курсу |
|--------------|---------------------|-----------------|
| **несумісна** зміна публічного інтерфейсу (контракту) | **MAJOR**, решту скинути в 0 (`1.4.2 → 2.0.0`) | метод `withdraw(amount)` став `withdraw(amount, currency)`; видалено клас; змінено тип винятку, який ловлять клієнти |
| **нова можливість**, старий код працює без змін | **MINOR**, PATCH → 0 (`1.4.2 → 1.5.0`) | новий клас `EmployeeDiscount` (принцип O); новий необов'язковий параметр зі значенням за замовчуванням |
| **виправлення помилки** без зміни інтерфейсу | **PATCH** (`1.4.2 → 1.4.3`) | `Stack.pop()` повертав не той елемент; виправлена перевірка в сеттері |

Правила:

- **публічний інтерфейс** — це все, на що можуть спиратися інші:
  публічні класи, методи, винятки, формати файлів. Приватні `_деталі`
  змінювати можна без підвищення MAJOR;
- версія `0.y.z` — «початкова розробка», нестабільна; `1.0.0` означає
  «інтерфейс стабільний і ми його підтримуємо»;
- **pre-release**: `1.2.0-alpha.1`, `1.2.0-rc.1` — **менші** за відповідний
  `1.2.0`; порядок: `1.0.0-alpha < 1.0.0-rc.1 < 1.0.0`;
- опублікована версія **незмінна**: помилку виправляють новою версією,
  а не перезаписом;
- прості зміни, що не торкаються поведінки (коментарі, рефакторинг
  усередині), нової версії не потребують — вони потраплять у наступну.

### Порядок версій

Версії порівнюють **за числами**, а не як рядки: `1.10.0 > 1.9.0`
(рядково було б навпаки). Саме це робить клас `Version` із задачі 4.8.

### Теги й журнал змін

- Кожен реліз позначають **git-тегом** `v1.2.0` на конкретному коміті:
  `git tag -a v1.2.0 -m "Release 1.2.0"`.
- Файл **`CHANGELOG.md`** (формат Keep a Changelog) записує зміни для
  людей, найновіші — угорі:

```markdown
## [1.5.0] - 2026-10-20
### Added
- `EmployeeDiscount` для знижок працівникам.
### Fixed
- `Stack.pop()` повертав останній елемент без видалення.

## [2.0.0] - 2026-11-02
### Changed
- **BREAKING:** `withdraw(amount)` тепер приймає `currency`.
```

Розділи: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.
Позначка **BREAKING** разом із MAJOR — сигнал користувачам.

### Як зробити зміну поступовою

Замість миттєвого видалення методу спершу позначте його **застарілим**
(`Deprecated`, попередження `warnings.warn(..., DeprecationWarning)`) у
MINOR-версії, а видаліть у наступній MAJOR. Це дає користувачам час
перейти.

```python
import warnings

def old_total(self):
    warnings.warn("використовуйте total()", DeprecationWarning, stacklevel=2)
    return self.total()
```

### Версія в коді

Зберігайте номер версії **в одному місці** (наприклад, `__version__ =
"1.2.0"` у пакеті або поле у `pyproject.toml`), а не розсипайте по файлах.
У JavaScript це `version` у `package.json`, у C++ — константа у
заголовку або `project(... VERSION 1.2.0)` у CMake.

> Версія — це **обіцянка про сумісність**. Тому дизайн, який рідко
> змінює публічні контракти (SOLID, GRASP: Protected Variations),
> дозволяє рідше підвищувати MAJOR.

## 13.14 Порівняння з іншими мовами

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Singleton | `__new__`, модуль | модуль / замикання | `static T& instance()` (Meyers singleton, потокобезпечний з C++11) |
| Factory | реєстр класів/функцій | реєстр/`Map` | `std::function`-реєстр, `unique_ptr<Base>` |
| Observer | список колбеків | `EventEmitter`, колбеки | `std::function`, `weak_ptr` для відписки |
| Decorator | обгортка того самого інтерфейсу | так само | так само, з `unique_ptr<Base>` усередині |
| Command | клас або замикання | замикання | клас або `std::function` |

Функції першого класу (Python, JS) спрощують Strategy, Command, Observer:
замість класу можна передати функцію.

## 13.15 Питання для самоперевірки

1. Чим патерн відрізняється від бібліотеки та від алгоритму?
2. Чому Singleton називають «глобальним станом» і чим це шкодить тестам?
3. Чим Decorator відрізняється від успадкування?
4. Які патерни реалізують принцип відкритості/закритості?
5. Як Command допомагає реалізувати «Скасувати»?
6. Яку цифру версії підвищити, якщо метод втратив параметр? Якщо додано новий клас? Якщо виправлено помилку?
7. Чому `1.10.0` новіша за `1.9.0` і навіщо потрібен `CHANGELOG.md`?
