# Chapter 13. Design Patterns and the Final Project

## 13.1 What Is a Design Pattern

A **pattern** is a typical, proven way of solving a typical
design problem. It is not ready-made code but a **template** that is adapted to the task.
The "Gang of Four" catalog (GoF, 1994) lists 23 patterns in three groups:

| Group | Question | Examples |
|-------|----------|----------|
| **Creational** | how to create objects | Singleton, Factory, Builder |
| **Structural** | how to compose objects into structures | Adapter, Decorator, Composite |
| **Behavioral** | how objects interact | Strategy, Observer, Command, State |

A pattern = **a name + a problem + a solution + consequences**. The benefit of a name:
the phrase "this is an Observer" conveys a whole design in two words.

> Do not apply a pattern "for the sake of the pattern". Start with a simple implementation;
> a pattern appears when **real pain** arises (duplication,
> tight coupling, inability to extend).

## 13.2 Singleton

Guarantees a **single instance** of a class and a global point of access.

**Python**

```python
class AppConfig:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.values = {}
        return cls._instance

AppConfig() is AppConfig()      # True
```

**JavaScript** — the simplest way is to export a single object from a
module; as a class:

```js
class AppConfig {
    static #instance = null;

    static instance() {
        AppConfig.#instance ??= new AppConfig();
        return AppConfig.#instance;
    }

    values = {};
}

AppConfig.instance() === AppConfig.instance();   // true
```

**C++** — the Meyers singleton (thread-safe since C++11):

```cpp
class AppConfig {
public:
    static AppConfig& instance() {
        static AppConfig config;        // created only once
        return config;
    }

    AppConfig(const AppConfig&) = delete;           // copying is forbidden
    AppConfig& operator=(const AppConfig&) = delete;

    std::map<std::string, std::string> values;

private:
    AppConfig() = default;
};

&AppConfig::instance() == &AppConfig::instance();   // true
```

A caveat: this is **global state** — it complicates testing. It is often better to
pass the single object through the constructor (Dependency Injection, chapter 8).
In Python a plain **module** often serves as a singleton.

> **Language difference: how to get a "second" singleton by accident.**
> In Python the isolation comes from `__new__`, and in JS a module runs
> only once, so the exported object is always the same. In C++ a plain
> assignment **copies** the object:
>
> ```cpp
> AppConfig cfg = AppConfig::instance();    // without "= delete" — a silent COPY
> AppConfig& ref = AppConfig::instance();   // correct — a reference
> ```
>
> That is exactly why the copy constructor is deleted (`= delete`) in the
> example above: then the first line does not compile.

## 13.3 Factory

Encapsulates object creation: the client asks to "create a circle" without knowing
the concrete class.

**Python**

```python
class ShapeFactory:
    _registry = {}

    @classmethod
    def register(cls, kind, creator): cls._registry[kind] = creator

    @classmethod
    def create(cls, kind, *args):
        return cls._registry[kind](*args)
```

**JavaScript**

```js
class ShapeFactory {
    static #registry = new Map();

    static register(kind, creator) { this.#registry.set(kind, creator); }

    static create(kind, ...args) {
        return this.#registry.get(kind)(...args);
    }
}

ShapeFactory.register("circle", (r) => new Circle(r));
```

**C++**

```cpp
#include <functional>
#include <map>
#include <memory>

class ShapeFactory {
public:
    using Creator = std::function<std::unique_ptr<Shape>(double)>;

    static void registerKind(const std::string& kind, Creator creator) {
        registry()[kind] = creator;
    }

    static std::unique_ptr<Shape> create(const std::string& kind, double arg) {
        return registry().at(kind)(arg);
    }

private:
    static std::map<std::string, Creator>& registry() {
        static std::map<std::string, Creator> r;
        return r;
    }
};

ShapeFactory::registerKind("circle", [](double r) { return std::make_unique<Circle>(r); });
```

The registry makes the factory **open for extension** (principle O): a new
kind is just `register(...)`, with no edits to the factory itself.

## 13.4 Builder

Assembles a complex object step by step; separates **construction** from
**representation**. Useful when a constructor has a dozen optional
parameters.

**Python**

```python
pizza = (PizzaBuilder().size(30).sauce("tomato")
         .topping("cheese").topping("mushrooms").build())
```

**JavaScript**

```js
const pizza = new PizzaBuilder().size(30).sauce("tomato")
    .topping("cheese").topping("mushrooms").build();
```

**C++**

```cpp
Pizza pizza = PizzaBuilder().size(30).sauce("tomato")
    .topping("cheese").topping("mushrooms").build();
```

`build()` checks the required parameters and returns the finished (often immutable)
object.

## 13.5 Adapter

Converts **the interface of one class into the interface the client expects**.
Used to integrate old or third-party code.

**Python**

```python
class FahrenheitSensorAdapter(TemperatureSensor):
    def __init__(self, legacy): self._legacy = legacy
    def celsius(self): return (self._legacy.read_fahrenheit() - 32) * 5 / 9
```

**JavaScript**

```js
class FahrenheitSensorAdapter {
    constructor(legacy) { this.legacy = legacy; }
    celsius() { return (this.legacy.readFahrenheit() - 32) * 5 / 9; }
}
```

**C++**

```cpp
class FahrenheitSensorAdapter : public TemperatureSensor {
public:
    explicit FahrenheitSensorAdapter(LegacySensor& legacy) : legacy(legacy) {}
    double celsius() const override {
        return (legacy.readFahrenheit() - 32) * 5 / 9;
    }
private:
    LegacySensor& legacy;
};
```

## 13.6 Decorator

Dynamically **adds behavior** to an object by **wrapping** it
in an object with the same interface. An alternative to inheritance without an
"explosion" of subclasses.

**Python**

```python
coffee = Caramel(Milk(Espresso()))      # nested wrappers
coffee.cost()                           # the sum of all layers
```

**JavaScript**

```js
class Milk {
    constructor(inner) { this.inner = inner; }
    cost() { return this.inner.cost() + 10; }
}

const coffee = new Caramel(new Milk(new Espresso()));   // nested wrappers
coffee.cost();                                          // the sum of all layers
```

**C++** — the wrapper owns the inner object through `unique_ptr`:

```cpp
class Milk : public Beverage {
public:
    explicit Milk(std::unique_ptr<Beverage> inner) : inner(std::move(inner)) {}
    double cost() const override { return inner->cost() + 10; }
private:
    std::unique_ptr<Beverage> inner;
};

auto coffee = std::make_unique<Caramel>(
    std::make_unique<Milk>(std::make_unique<Espresso>()));   // nested wrappers
coffee->cost();                                              // the sum of all layers
```

(Do not confuse it with Python's `@decorator` syntax for functions — it is a related
but different idea.)

## 13.7 Strategy

A family of interchangeable algorithms behind a **common interface**; the client
chooses and swaps them at run time (chapter 11, principle O).

**Python**

```python
sorter = Sorter(MergeSort())
sorter.strategy = BubbleSort()          # swapped "on the fly"
```

**JavaScript** — a strategy can also be just a function:

```js
const sorter = new Sorter(new MergeSort());
sorter.strategy = new BubbleSort();     // swapped "on the fly"
```

**C++**

```cpp
Sorter sorter(std::make_unique<MergeSort>());
sorter.setStrategy(std::make_unique<BubbleSort>());   // swapped "on the fly"
```

## 13.8 Observer

A **subject** object notifies a list of **subscribers** about a state change
without knowing their classes — loose coupling. The basis of events, GUIs,
and reactive programming.

**Python**

```python
stock.attach(logger); stock.attach(alert)
stock.set_price(105)           # all subscribers get notified
```

**JavaScript** — subscribers are often plain functions:

```js
class Stock {
    #observers = [];
    attach(fn) { this.#observers.push(fn); }
    setPrice(price) {
        this.price = price;
        this.#observers.forEach((fn) => fn(price));   // notification
    }
}

stock.attach((p) => console.log("price", p));
stock.setPrice(105);
```

**C++**

```cpp
#include <functional>
#include <vector>

class Stock {
public:
    void attach(std::function<void(double)> fn) { observers.push_back(fn); }
    void setPrice(double p) {
        price = p;
        for (auto& fn : observers) fn(p);           // notification
    }
private:
    double price = 0;
    std::vector<std::function<void(double)>> observers;
};

stock.attach([](double p) { std::cout << "price " << p << "\n"; });
stock.setPrice(105);
```

Typical risks: forgotten unsubscriptions (memory leaks), the order of notifications,
cascading updates.

## 13.9 Command

Encapsulates a **request as an object**: it can be queued, logged,
and **undone**.

**Python**

```python
class Command(ABC):
    def execute(self): ...
    def undo(self): ...

history.execute(InsertCommand(editor, "Hello"))
history.undo()
```

**JavaScript**

```js
class Command {
    execute() {}
    undo() {}
}

history.execute(new InsertCommand(editor, "Hello"));
history.undo();
```

**C++**

```cpp
class Command {
public:
    virtual ~Command() = default;
    virtual void execute() = 0;
    virtual void undo() = 0;
};

history.execute(std::make_unique<InsertCommand>(editor, "Hello"));
history.undo();
```

## 13.10 State

An object changes its behavior when its internal state changes: instead of huge
`if status == ...` chains, each state is a **separate class** that knows the allowed
transitions.

**Python**

```python
class Paid(OrderState):
    def ship(self, order): order.state = Shipped()
    def pay(self, order):  raise InvalidTransition("already paid")
```

**JavaScript**

```js
class Paid extends OrderState {
    ship(order) { order.state = new Shipped(); }
    pay(order)  { throw new InvalidTransition("already paid"); }
}
```

**C++**

```cpp
class Paid : public OrderState {
public:
    void ship(Order& order) override { order.setState(std::make_unique<Shipped>()); }
    void pay(Order&) override { throw InvalidTransition("already paid"); }
};
```

## 13.11 Patterns and Principles

| Pattern | Implements the principle |
|---------|--------------------------|
| Strategy, Decorator, Factory (registry) | **O** — extension without modification |
| Adapter | **D**, **I** — the client depends on its own interface |
| Observer | **D** — loose coupling of the subject and subscribers |
| Builder | **S** — a separate object for construction |
| State, Command | **S**, **O** — each variant of behavior in a separate class |

## 13.13 Product Versioning

Once a project has users (even one), they need to know **whether it is safe
to upgrade**. The version number tells them. The standard is
**semantic versioning** (SemVer, semver.org): `MAJOR.MINOR.PATCH`,
for example `2.4.1`.

| What changed | Which number to bump | Example from the course |
|--------------|----------------------|-------------------------|
| an **incompatible** change to the public interface (the contract) | **MAJOR**, reset the rest to 0 (`1.4.2 → 2.0.0`) | the method `withdraw(amount)` became `withdraw(amount, currency)`; a class was removed; the exception type that clients catch was changed |
| a **new feature**, old code works unchanged | **MINOR**, PATCH → 0 (`1.4.2 → 1.5.0`) | a new class `EmployeeDiscount` (principle O); a new optional parameter with a default value |
| a **bug fix** with no interface change | **PATCH** (`1.4.2 → 1.4.3`) | `Stack.pop()` returned the wrong element; a check in a setter was fixed |

Rules:

- the **public interface** is everything others can rely on:
  public classes, methods, exceptions, file formats. Private `_details`
  can change without bumping MAJOR;
- a `0.y.z` version means "initial development", unstable; `1.0.0` means
  "the interface is stable and we support it";
- **pre-release**: `1.2.0-alpha.1`, `1.2.0-rc.1` — they sort *before* the matching
  `1.2.0`, not after; the order is `1.0.0-alpha < 1.0.0-rc.1 < 1.0.0`;
- a published version is **immutable**: a mistake is fixed with a new version,
  not by overwriting;
- simple changes that do not affect behavior (comments, internal
  refactoring) do not need a new version — they ship in the next one.

### Version Ordering

Versions are compared **numerically**, not as strings: `1.10.0 > 1.9.0`
(as strings it would be the other way round). This is exactly what the `Version`
class from task 4.8 does.

### Tags and the Changelog

- Mark every release with a **git tag** `v1.2.0` on a specific commit:
  `git tag -a v1.2.0 -m "Release 1.2.0"`.
- A **`CHANGELOG.md`** file (the Keep a Changelog format) records changes for
  humans, newest first:

```markdown
## [1.5.0] - 2026-10-20
### Added
- `EmployeeDiscount` for employee discounts.
### Fixed
- `Stack.pop()` returned the last element without removing it.

## [2.0.0] - 2026-11-02
### Changed
- **BREAKING:** `withdraw(amount)` now takes `currency`.
```

Sections: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.
The **BREAKING** mark together with MAJOR is a signal to users.

### Making a Change Gradual

Instead of removing a method at once, first mark it **deprecated**
(`Deprecated`, a `warnings.warn(..., DeprecationWarning)` warning) in a
MINOR version, and remove it in the next MAJOR. This gives users time to
migrate.

**Python**

```python
import warnings

def old_total(self):
    warnings.warn("use total()", DeprecationWarning, stacklevel=2)
    return self.total()
```

**JavaScript** — the JSDoc tag `@deprecated` (editors strike the call
through) plus a console warning:

```js
/** @deprecated use total() */
oldTotal() {
    console.warn("oldTotal() is deprecated: use total()");
    return this.total();
}
```

**C++** — the `[[deprecated]]` attribute produces a **compiler** warning:

```cpp
[[deprecated("use total()")]]
double oldTotal() const { return total(); }
```

### The Version in Code

Keep the version number **in one place** (for example, `__version__ =
"1.2.0"` in the package or a field in `pyproject.toml`) rather than scattering it across files.
In JavaScript it is `version` in `package.json`, in C++ a constant in a
header or `project(... VERSION 1.2.0)` in CMake.

> A version is a **promise about compatibility**. That is why a design that rarely
> changes its public contracts (SOLID, GRASP: Protected Variations)
> lets you bump MAJOR less often.

## 13.14 Comparison with Other Languages

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Singleton | `__new__`, a module | a module / closure | `static T& instance()` (Meyers singleton, thread-safe since C++11) |
| Factory | a registry of classes/functions | a registry/`Map` | a `std::function` registry, `unique_ptr<Base>` |
| Observer | a list of callbacks | `EventEmitter`, callbacks | `std::function`, `weak_ptr` for unsubscribing |
| Decorator | a wrapper with the same interface | the same | the same, with a `unique_ptr<Base>` inside |
| Command | a class or a closure | a closure | a class or `std::function` |

First-class functions (Python, JS) simplify Strategy, Command, and Observer:
you can pass a function instead of a class.
