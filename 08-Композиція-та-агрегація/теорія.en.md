# Chapter 8. Composition and Aggregation

## 8.1 The "Has-a" Relationship

Inheritance expresses "is a" (is-a): a dog is an animal. But often
the relationship is different: a car **has** an engine, a library **has** books.
Then one object stores **references to other objects** — this is
**composition** in the broad sense (object composition).

```python
class Engine:
    def __init__(self, hp): self.hp, self.running = hp, False
    def start(self): self.running = True

class Car:
    def __init__(self, brand, hp):
        self.brand = brand
        self.engine = Engine(hp)      # Car "has" an Engine
```

## 8.2 Composition and Aggregation

UML distinguishes two kinds of "whole — part" relationship:

| | **Composition** (◆) | **Aggregation** (◇) |
|---|---|---|
| Ownership | the whole **owns** the part | the whole only **refers** to the part |
| Lifetime | the part lives and dies with the whole | the part exists independently |
| Creation | the whole creates the part itself | the part is created outside and passed in |
| Sharing | the part belongs to exactly one whole | the part can be shared by several wholes |
| Example | `Car` — `Engine`, `Order` — `OrderLine` | `Library` — `Book`, `Team` — `Employee` |

```python
class Library:                         # aggregation: books come from outside
    def __init__(self): self.books = []
    def add(self, book): self.books.append(book)

class Order:                           # composition: Order creates the lines itself
    def __init__(self): self._lines = []
    def add(self, product, qty): self._lines.append(OrderLine(product, qty))
```

The boundary is blurry and depends on the problem domain; what matters is to decide
**consciously** who owns what.

## 8.3 Delegation

The "whole" object forwards part of the work to the "part" object:

```python
class Car:
    def start(self):
        self.engine.start()            # delegation
```

Delegation lets you expose only the interface you need. Example:
a stack that **contains** a list rather than **inheriting** from it — from outside
there are no superfluous `insert`, `remove`, `sort`.

## 8.4 Composition Instead of Inheritance

Problems with inheritance: tight coupling to the parent, a "class explosion"
(`FlyingSwimmingRobotDuck`), Liskov violations. Composition gives:

- **flexibility** — behavior can be changed at run time;
- **reuse** without deep hierarchies;
- **easier testing** — parts can be substituted.

An example is the component approach in games: an entity (`Entity`) consists
of components `Health`, `Mover`, `Attacker`; an enemy, a tower, and a player are different
sets of components, not branches of a class tree.

> Rule: **prefer composition** over inheritance
> (Gang of Four). Use inheritance only when "is-a" is truly natural.

## 8.5 Dependency Injection

Instead of creating a part inside, **pass it in from outside**:

```python
class Notifier:
    def __init__(self, transport):     # the dependency is "injected"
        self.transport = transport

    def notify(self, user, text):
        return self.transport.send(user, text)
```

In production we pass `SmtpTransport`, in a test — `FakeTransport`.
`Notifier` does not know what it works with — only that it has `send`.

## 8.6 Recursive Composition

A part can be of the same type as the whole — this forms a **tree**
(a file system, a menu, the DOM):

```python
class Folder:
    def __init__(self, name): self.name, self.children = name, []
    def size(self): return sum(c.size() for c in self.children)
```

## 8.7 Copying Complex Objects

```python
import copy
b = copy.copy(a)        # shallow: new "wrappers", the same nested objects
c = copy.deepcopy(a)    # deep: a fully independent copy of the whole graph
```

Composition usually needs a **deep** copy (the parts belong to the
whole), aggregation sometimes a shallow one (the parts are shared).

## 8.8 The Law of Demeter

"Talk only to your close friends": a method should only call
`self`, its attributes, its parameters, and objects it created.
Chains like `car.engine.fuel_pump.valve.open()` are a sign of a violation;
add a delegating method to `Car`.

## 8.9 Comparison with Other Languages

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Composition | an object attribute | an object field | a **value member** `Engine engine;` (lives inside) |
| Aggregation | a reference | a reference | a pointer/reference `Book*`, `shared_ptr<Book>` |
| Lifetime | garbage collector | garbage collector | **deterministic**: the whole's destructor destroys its members |
| Ownership | implicit | implicit | `unique_ptr` (owns), `shared_ptr` (shares), `weak_ptr` (does not own) |

In C++ the difference between composition and aggregation is **visible in the code**:
`Engine engine;` or `unique_ptr<Engine>` is composition;
`Book*` / `shared_ptr<Book>` is aggregation.
