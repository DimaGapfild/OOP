# Розділ 8. Композиція та агрегація

## 8.1 Відношення «має» (has-a)

Успадкування виражає «є» (is-a): собака — це тварина. Але часто
зв'язок інший: автомобіль **має** двигун, бібліотека **має** книги.
Тоді один об'єкт зберігає **посилання на інші об'єкти** — це
**композиція** у широкому сенсі (об'єктна композиція).

**Python**

```python
class Engine:
    def __init__(self, hp): self.hp, self.running = hp, False
    def start(self): self.running = True

class Car:
    def __init__(self, brand, hp):
        self.brand = brand
        self.engine = Engine(hp)      # Car «має» Engine
```

**JavaScript**

```js
class Engine {
    constructor(hp) { this.hp = hp; this.running = false; }
    start() { this.running = true; }
}

class Car {
    constructor(brand, hp) {
        this.brand = brand;
        this.engine = new Engine(hp);   // Car «має» Engine
    }
}
```

**C++**

```cpp
class Engine {
public:
    explicit Engine(int hp) : hp(hp) {}
    void start() { running = true; }
private:
    int hp;
    bool running = false;
};

class Car {
public:
    Car(std::string brand, int hp) : brand(brand), engine(hp) {}
private:
    std::string brand;
    Engine engine;                      // Car «має» Engine (всередині об'єкта)
};
```

## 8.2 Композиція та агрегація

UML розрізняє два різновиди зв'язку «ціле — частина»:

| | **Композиція** (◆) | **Агрегація** (◇) |
|---|---|---|
| Володіння | ціле **володіє** частиною | ціле лише **посилається** на частину |
| Час життя | частина живе й помирає разом із цілим | частина існує незалежно |
| Створення | частину створює саме ціле | частину створюють зовні й передають |
| Спільність | частина належить рівно одному цілому | частину можуть ділити кілька цілих |
| Приклад | `Car` — `Engine`, `Order` — `OrderLine` | `Library` — `Book`, `Team` — `Employee` |

**Python**

```python
class Library:                         # агрегація: книги приходять ззовні
    def __init__(self): self.books = []
    def add(self, book): self.books.append(book)

class Order:                           # композиція: рядки створює сам Order
    def __init__(self): self._lines = []
    def add(self, product, qty): self._lines.append(OrderLine(product, qty))
```

**JavaScript**

```js
class Library {                        // агрегація: книги приходять ззовні
    constructor() { this.books = []; }
    add(book) { this.books.push(book); }
}

class Order {                          // композиція: рядки створює сам Order
    #lines = [];
    add(product, qty) { this.#lines.push(new OrderLine(product, qty)); }
}
```

**C++** — різницю видно з типів полів:

```cpp
#include <memory>
#include <vector>

class Library {                        // агрегація: не володіє книгами
public:
    void add(std::shared_ptr<Book> book) { books.push_back(book); }
private:
    std::vector<std::shared_ptr<Book>> books;
};

class Order {                          // композиція: рядки — частина Order
public:
    void add(const Product& product, int qty) {
        lines.emplace_back(product, qty);
    }
private:
    std::vector<OrderLine> lines;      // знищуються разом з Order
};
```

Межа розмита й залежить від предметної області; важливо **свідомо**
вирішувати, хто чим володіє.

> **Різниця між мовами: хто стежить за часом життя частин.** У Python і
> JavaScript об'єкт живе, доки на нього є хоч одне посилання (збирач
> сміття). У C++ агрегація через звичайне посилання чи вказівник
> небезпечна:
>
> ```cpp
> Library lib;             // варіант Library, що зберігає std::vector<Book*>
> {
>     Book b("Кобзар", 320);
>     lib.add(&b);         // зберігаємо лише адресу
> }                        // b знищено — у бібліотеці «висяче» посилання
> lib.totalPages();        // невизначена поведінка: може впасти, може «працювати»
> ```
>
> Тому спільні частини в C++ зберігають у `shared_ptr`, а для
> композиції використовують поле-значення або `unique_ptr`.

## 8.3 Делегування

Об'єкт-«ціле» перенаправляє частину роботи об'єктові-«частині»:

**Python**

```python
class Car:
    def start(self):
        self.engine.start()            # делегування
```

**JavaScript**

```js
class Car {
    start() {
        this.engine.start();           // делегування
    }
}
```

**C++**

```cpp
class Car {
public:
    void start() {
        engine.start();                // делегування
    }
private:
    Engine engine;
};
```

Делегування дозволяє показати лише потрібний інтерфейс. Приклад:
стек, що **містить** список, а не **успадковує** від нього — зовні
немає зайвих `insert`, `remove`, `sort`.

## 8.4 Композиція замість успадкування

Проблеми успадкування: жорсткий зв'язок із предком, «вибух» класів
(`FlyingSwimmingRobotDuck`), порушення Лісков. Композиція дає:

- **гнучкість** — поведінку можна міняти під час виконання;
- **повторне використання** без глибоких ієрархій;
- **простіше тестування** — частини підміняються.

Приклад — компонентний підхід у іграх: сутність (`Entity`) складається
з компонентів `Health`, `Mover`, `Attacker`; ворог, вежа й гравець — різні
набори компонентів, а не гілки дерева класів.

> Правило: **віддавайте перевагу композиції** над успадкуванням
> (Gang of Four). Успадкування — лише коли «є» справді природне.

## 8.5 Впровадження залежностей (Dependency Injection)

Замість створення частини всередині — **передаємо її зовні**:

**Python**

```python
class Notifier:
    def __init__(self, transport):     # залежність «впроваджується»
        self.transport = transport

    def notify(self, user, text):
        return self.transport.send(user, text)
```

**JavaScript**

```js
class Notifier {
    constructor(transport) {           // залежність «впроваджується»
        this.transport = transport;
    }

    notify(user, text) {
        return this.transport.send(user, text);
    }
}
```

**C++**

```cpp
class Transport {
public:
    virtual ~Transport() = default;
    virtual bool send(const std::string& user, const std::string& text) = 0;
};

class Notifier {
public:
    explicit Notifier(Transport& transport)    // залежність «впроваджується»
        : transport(transport) {}

    bool notify(const std::string& user, const std::string& text) {
        return transport.send(user, text);
    }

private:
    Transport& transport;
};
```

У проді передаємо `SmtpTransport`, у тесті — `FakeTransport`.
`Notifier` не знає, з чим працює, — лише що в нього є `send`.

## 8.6 Рекурсивна композиція

Частина може бути того ж типу, що й ціле — утворюється **дерево**
(файлова система, меню, DOM):

**Python**

```python
class Folder:
    def __init__(self, name): self.name, self.children = name, []
    def size(self): return sum(c.size() for c in self.children)
```

**JavaScript**

```js
class Folder {
    constructor(name) { this.name = name; this.children = []; }
    size() { return this.children.reduce((sum, c) => sum + c.size(), 0); }
}
```

**C++** — дерево володіє дітьми через `unique_ptr`:

```cpp
#include <memory>
#include <vector>

class Node {
public:
    virtual ~Node() = default;
    virtual long size() const = 0;
};

class Folder : public Node {
public:
    void add(std::unique_ptr<Node> child) { children.push_back(std::move(child)); }

    long size() const override {
        long sum = 0;
        for (const auto& c : children) sum += c->size();
        return sum;
    }

private:
    std::vector<std::unique_ptr<Node>> children;
};
```

## 8.7 Копіювання складних об'єктів

**Python**

```python
import copy
b = copy.copy(a)        # поверхнева: нові «обгортки», ті самі вкладені об'єкти
c = copy.deepcopy(a)    # глибока: повністю незалежна копія всього графа
```

**JavaScript**

```js
const b = { ...a };               // поверхнева: вкладені об'єкти спільні
const c = structuredClone(a);     // глибока (лише дані, без методів класу)
```

**C++** — копіювання **значень** глибоке автоматично: копіюються всі
члени, зокрема `std::vector` і вкладені об'єкти. Поверхневою копія стає
лише для вказівників (`Book*`, `shared_ptr<Book>`):

```cpp
Order b = a;                      // нові рядки замовлення — незалежна копія
Library l2 = l1;                  // нові вектори, але ті самі книги (shared_ptr)
```

Для композиції зазвичай потрібна **глибока** копія (частини належать
цілому), для агрегації — інколи поверхнева (частини спільні).

> **Різниця між мовами: що робить звичайне присвоєння.**
>
> | | Python | JavaScript | C++ |
> |---|---|---|---|
> | `b = a` | спільне посилання | спільне посилання | **глибока копія** членів-значень |
> | Незалежна копія | `copy.deepcopy(a)` | `structuredClone(a)` (лише дані) | `Car b = a;` — за замовчуванням |
>
> Студенти, що переходять з C++ на Python/JS, часто очікують копію,
> а отримують спільний об'єкт — і навпаки.

## 8.8 Закон Деметри

«Говори лише з близькими друзями»: метод має звертатися лише до
`self`, своїх атрибутів, параметрів і створених ним об'єктів.
Ланцюжки `car.engine.fuel_pump.valve.open()` — ознака порушення;
додайте метод-делегат у `Car`.

## 8.9 Порівняння з іншими мовами

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Композиція | атрибут-об'єкт | поле-об'єкт | **член-значення** `Engine engine;` (живе всередині) |
| Агрегація | посилання | посилання | вказівник/посилання `Book*`, `shared_ptr<Book>` |
| Час життя | збирач сміття | збирач сміття | **детерміновано**: деструктор цілого знищує члени |
| Володіння | неявне | неявне | `unique_ptr` (володіє), `shared_ptr` (ділить), `weak_ptr` (не володіє) |

У C++ різниця між композицією й агрегацією **видна в коді**:
`Engine engine;` або `unique_ptr<Engine>` — композиція;
`Book*` / `shared_ptr<Book>` — агрегація.
