# Chapter 12. GRASP: Principles of Assigning Responsibilities

## 12.1 What Is GRASP

**GRASP** (General Responsibility Assignment Software Patterns) is a set of
nine principles by Craig Larman that answer the central question of
object-oriented design: **"which class should be responsible for this action?"**

Responsibilities come in two kinds:

- **knowing** — holding data, knowing related objects, being able to compute something;
- **doing** — performing an action, creating objects, controlling others.

SOLID (chapter 11) evaluates a **finished** design; GRASP helps you **make the
decision** while designing. Some principles echo each other
(Low Coupling ↔ DIP, High Cohesion ↔ SRP, Polymorphism ↔ OCP), while others —
Information Expert, Creator, Controller — give a new hint: where to put a method.

| No. | Principle | In short |
|-----|-----------|----------|
| 1 | Information Expert | the responsibility goes to whoever has the necessary data |
| 2 | Creator | an object is created by whoever contains or uses it |
| 3 | Controller | the first object after the UI that receives a system event |
| 4 | Low Coupling | as few dependencies between classes as possible |
| 5 | High Cohesion | a class does one coherent job |
| 6 | Polymorphism | variants of behavior via polymorphism, not an `if` on the type |
| 7 | Pure Fabrication | an artificial class that is not in the problem domain, for the sake of low coupling |
| 8 | Indirection | an intermediary between two objects so they do not know about each other |
| 9 | Protected Variations | a stable interface around an unstable spot |

## 12.2 Information Expert

> Give a responsibility to the class that has the **information** needed
> to fulfill it.

Who computes an order's total? A line knows the price and quantity, the order knows
the lines and the discount:

**Python**

```python
class OrderLine:
    def subtotal(self): return self.product.price * self.qty

class Order:
    def total(self):
        return sum(l.subtotal() for l in self.lines) * (1 - self.discount)
```

**JavaScript**

```js
class OrderLine {
    subtotal() { return this.product.price * this.qty; }
}

class Order {
    total() {
        const sum = this.lines.reduce((s, l) => s + l.subtotal(), 0);
        return sum * (1 - this.discount);
    }
}
```

**C++**

```cpp
class OrderLine {
public:
    double subtotal() const { return product.price * qty; }
private:
    Product product;
    int qty;
};

class Order {
public:
    double total() const {
        double sum = 0;
        for (const auto& l : lines) sum += l.subtotal();
        return sum * (1 - discount);
    }
private:
    std::vector<OrderLine> lines;
    double discount = 0;
};
```

A sign of violation is an external "manager" that pulls data out of objects
with getters and computes on their behalf (`OrderCalculator.total(order)`).
Result: encapsulation is preserved, and data and behavior sit side by side.

## 12.3 Creator

> Class **B** creates objects of **A** if: B contains (aggregates) A; B
> records A; B closely uses A; B has the data to initialize A.

`Course.enroll(student)` creates an `Enrollment`: the course contains the records and has
all the data (capacity, the list) for the checks. The client does not call
`Enrollment(...)` directly — the "whole — part" relationship (chapter 8) stays
under the whole's control. If creation is complex, use a Factory or Builder
(chapter 13).

## 12.4 Controller

> A system event (a user request, a command, an HTTP request) is received
> **not by the UI** but by a separate controller object.

Options: a **use-case controller** (one per scenario:
`BookingController`) or a **facade controller** (represents the whole system). The controller
**coordinates** — hands the work to domain objects and returns the
result; it **contains no business logic itself**.

```
UI  ──simple data──►  Controller  ──►  Model (Session, Order, ...)
UI  ◄──simple result──  Controller
```

A typical mistake is a "bloated controller" that computes, validates, and stores
everything itself. It then violates High Cohesion.

## 12.5 Low Coupling

> Minimize dependencies between classes: a change in one should not
> "echo" through many others.

Kinds of coupling (worst first): knows the internal structure → depends on a
concrete class → depends on an interface. Techniques:

- do not walk chains like `customer.address.city.name` (the Law of Demeter,
  chapter 8) — add a delegate `customer.city_name()`;
- depend on an **abstraction**, not an implementation (DIP);
- pass dependencies in from outside (DI, chapter 8).

Low coupling is an **evaluative** principle: it is used to check other decisions.

## 12.6 High Cohesion

> A class's responsibilities should be **closely related** and
> focused.

A `Utils` class with date, string, and statistics functions has low cohesion.
Splitting it into `Calendar`, `TextTools`, `Stats` gives classes whose name
explains everything. A practical test: can you describe the class in **one
sentence without "and"**? High cohesion ≈ SRP, but it is about the *relatedness* of a class,
not about "reasons to change".

## 12.7 Polymorphism

> When behavior depends on a **type**, do not check the type in `if`/`switch`
> — assign the variants of behavior **to the types** via polymorphic methods.

**Python**

```python
class Ticket(ABC):
    @abstractmethod
    def price(self, base): ...
```

**JavaScript**

```js
class Ticket {
    price(base) { throw new Error("not implemented"); }
}
```

**C++**

```cpp
class Ticket {
public:
    virtual ~Ticket() = default;
    virtual double price(double base) const = 0;
};
```

`total(tickets)` does not change when a `Group` ticket is added. This is an
implementation of OCP (chapter 11) and subtype polymorphism (chapter 6).

## 12.8 Pure Fabrication

> If the "natural" domain class (by Expert) violates Low
> Coupling or High Cohesion, create an **artificial** class.

There is no "invoice storage" in the real world, yet `InvoiceRepository`
frees `Invoice` from persistence (SRP) and hides how it is stored.
Typical fabrications: `Repository`, `Logger`, `Validator`, `Serializer`,
`PriceCalculator`. The risk is turning everything into "services" and ending up with an
"anemic model", where data is in one place and logic in another; keep Expert as the first
choice.

## 12.9 Indirection

> To decouple two objects, add an **intermediary**.

The intermediary is a `ChatRoom` between chat users, an adapter, a facade,
an event bus, a controller. Users know only the room, not each other;
adding a participant or changing the delivery mechanism is done in one place.
The proverb: "any problem in programming can be solved by another level of
indirection — except the problem of too many levels."

## 12.10 Protected Variations

> Find the points of **instability** and wrap them in a **stable
> interface**.

Currency rates, payment systems, file formats, databases — things that will certainly
change. `RateProvider` hides the source of rates; the client `Money.convert`
does not change when `CachedRates` or a real API appears. This is the
"core" of many patterns (Adapter, Strategy, Factory) and principles
(OCP, DIP) — the **most important** GRASP principle.

## 12.11 GRASP, Patterns, and SOLID

| GRASP | Implemented by patterns | Related SOLID |
|-------|-------------------------|---------------|
| Information Expert | — (a basic heuristic) | SRP |
| Creator | Factory, Builder | — |
| Controller | Facade, Command | SRP |
| Low Coupling | Observer, Mediator, DI | DIP |
| High Cohesion | — | SRP, ISP |
| Polymorphism | Strategy, State, Decorator | OCP, LSP |
| Pure Fabrication | Repository, Strategy | SRP |
| Indirection | Adapter, Facade, Mediator, Proxy | DIP |
| Protected Variations | Adapter, Strategy, Factory | OCP, DIP |

The principles can **conflict**: Expert advises putting persistence in
`Invoice`, whereas High Cohesion says not to; then Pure Fabrication wins. The art of
design lies in a balanced compromise, not in dogmatic application.

## 12.12 Comparison with Other Languages

GRASP is language-independent. Only the tools differ:

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Creator / Expert | methods of the owning class | the same | the same; ownership via `unique_ptr` |
| Low Coupling | duck typing, `Protocol` | duck typing | interfaces with `virtual`, templates |
| Polymorphism | any method is virtual | the same | `virtual` is mandatory |
| Protected Variations | `ABC` / `Protocol` | duck typing | an abstract class |
| Pure Fabrication | a repository class | the same | the same (+ RAII wrappers) |
