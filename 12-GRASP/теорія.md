# Розділ 12. GRASP: принципи розподілу відповідальностей

## 12.1 Що таке GRASP

**GRASP** (General Responsibility Assignment Software Patterns) — набір із
дев'яти принципів Крега Лармана для відповіді на головне питання
об'єктного проєктування: **«який клас має відповідати за цю дію?»**

Відповідальність буває двох видів:

- **знати** — тримати дані, знати пов'язані об'єкти, вміти щось обчислити;
- **робити** — виконувати дію, створювати об'єкти, керувати іншими.

SOLID (розділ 11) оцінює **готовий** дизайн; GRASP допомагає **прийняти
рішення** під час проєктування. Деякі принципи перегукуються
(Low Coupling ↔ DIP, High Cohesion ↔ SRP, Polymorphism ↔ OCP), інші —
Information Expert, Creator, Controller — дають нову підказку: куди покласти метод.

| № | Принцип | Коротко |
|---|---------|---------|
| 1 | Information Expert | відповідальність — у того, хто має потрібні дані |
| 2 | Creator | об'єкт створює той, хто його містить або використовує |
| 3 | Controller | перший після UI об'єкт, що приймає системну подію |
| 4 | Low Coupling | якомога менше залежностей між класами |
| 5 | High Cohesion | клас робить одну зв'язну справу |
| 6 | Polymorphism | варіанти поведінки — через поліморфізм, а не `if` по типу |
| 7 | Pure Fabrication | штучний клас, якого немає в предметній області, заради слабкого зв'язку |
| 8 | Indirection | посередник між двома об'єктами, щоб вони не знали один про одного |
| 9 | Protected Variations | стабільний інтерфейс навколо нестабільного місця |

## 12.2 Information Expert (експерт)

> Віддайте відповідальність класу, який має **інформацію**, потрібну
> для її виконання.

Хто рахує суму замовлення? Рядок знає ціну та кількість, замовлення знає
рядки та знижку:

**Python**

```python
class OrderLine:
    def subtotal(self): return self.product.price * self.qty

class Order:
    def total(self):
        return sum(l.subtotal() for l in self.lines) * (1 - self.discount)
```

**JavaScript**

```js
class OrderLine {
    subtotal() { return this.product.price * this.qty; }
}

class Order {
    total() {
        const sum = this.lines.reduce((s, l) => s + l.subtotal(), 0);
        return sum * (1 - this.discount);
    }
}
```

**C++**

```cpp
class OrderLine {
public:
    double subtotal() const { return product.price * qty; }
private:
    Product product;
    int qty;
};

class Order {
public:
    double total() const {
        double sum = 0;
        for (const auto& l : lines) sum += l.subtotal();
        return sum * (1 - discount);
    }
private:
    std::vector<OrderLine> lines;
    double discount = 0;
};
```

Ознака порушення — зовнішній «менеджер», що дістає з об'єктів дані
геттерами й рахує за них (`OrderCalculator.total(order)`).
Наслідок: інкапсуляція зберігається, дані й поведінка поруч.

## 12.3 Creator (творець)

> Клас **B** створює об'єкти **A**, якщо: B містить (агрегує) A; B
> записує A; B тісно використовує A; B має дані для ініціалізації A.

`Course.enroll(student)` створює `Enrollment`: курс містить записи й має
всі дані (місткість, список) для перевірок. Клієнт не викликає
`Enrollment(...)` напряму — зв'язок «ціле — частина» (розділ 8) лишається
під контролем цілого. Якщо створення складне — Factory чи Builder
(розділ 13).

## 12.4 Controller (контролер)

> Системну подію (запит користувача, команду, HTTP-запит) приймає
> **не UI**, а окремий об'єкт-контролер.

Варіанти: **use-case контролер** (по одному на сценарій:
`BookingController`) або **фасадний** (представляє всю систему). Контролер
**координує** — передає роботу об'єктам предметної області й повертає
результат; **сам бізнес-логіки не містить**.

```
UI  ──прості дані──►  Controller  ──►  Модель (Session, Order, ...)
UI  ◄──простий результат──  Controller
```

Типова помилка — «роздутий контролер», що рахує, перевіряє й зберігає
сам. Тоді він порушує High Cohesion.

## 12.5 Low Coupling (слабкий зв'язок)

> Мінімізуйте залежності між класами: зміна в одному не повинна
> «лунати» в багатьох інших.

Види зв'язку (від найгіршого): знає внутрішню будову → залежить від
конкретного класу → залежить від інтерфейсу. Прийоми:

- не ходити ланцюжками `customer.address.city.name` (закон Деметри,
  розділ 8) — додати делегат `customer.city_name()`;
- залежати від **абстракції**, а не від реалізації (DIP);
- передавати залежності ззовні (DI, розділ 8).

Слабкий зв'язок — це **оцінний** принцип: ним перевіряють інші рішення.

## 12.6 High Cohesion (високе зчеплення)

> Відповідальності класу мають бути **тісно пов'язані** та
> сфокусовані.

Клас `Utils` з функціями дат, рядків і статистики — низька зчепленість.
Розбиття на `Calendar`, `TextTools`, `Stats` дає класи, ім'я яких
пояснює все. Практичний тест: чи можна описати клас **одним реченням без
«і»**? Високе зчеплення ≈ SRP, але про *зв'язність* класу, а не про
«причини змін».

## 12.7 Polymorphism (поліморфізм)

> Коли поведінка залежить від **типу**, не перевіряйте тип у `if`/`switch`
> — призначте варіанти поведінки **типам** через поліморфні методи.

**Python**

```python
class Ticket(ABC):
    @abstractmethod
    def price(self, base): ...
```

**JavaScript**

```js
class Ticket {
    price(base) { throw new Error("не реалізовано"); }
}
```

**C++**

```cpp
class Ticket {
public:
    virtual ~Ticket() = default;
    virtual double price(double base) const = 0;
};
```

`total(tickets)` не змінюється, коли додається `Group`-квиток. Це
реалізація OCP (розділ 11) і підтипового поліморфізму (розділ 6).

## 12.8 Pure Fabrication (чиста вигадка)

> Якщо «природний» клас предметної області (за Expert) порушує Low
> Coupling чи High Cohesion — створіть **штучний** клас.

У реальному світі немає «сховища рахунків», проте `InvoiceRepository`
звільняє `Invoice` від збереження (SRP) і ховає спосіб зберігання.
Типові вигадки: `Repository`, `Logger`, `Validator`, `Serializer`,
`PriceCalculator`. Ризик — перетворити все на «сервіси» й отримати
«анемічну модель», де дані окремо, а логіка окремо; тримайте Expert першим
вибором.

## 12.9 Indirection (опосередкування)

> Щоб розв'язати зв'язок двох об'єктів, додайте **посередника**.

Посередник — `ChatRoom` між користувачами чату, адаптер, фасад,
шина подій, контролер. Користувачі знають лише кімнату, а не один одного;
додати учасника чи змінити спосіб доставки можна в одному місці.
Прислів'я: «будь-яку проблему в програмуванні можна розв'язати ще одним
рівнем опосередкування — крім проблеми надлишку рівнів».

## 12.10 Protected Variations (захист від варіацій)

> Знайдіть точки **нестабільності** та оберніть їх **стабільним
> інтерфейсом**.

Курси валют, платіжні системи, формати файлів, бази даних — те, що точно
зміниться. `RateProvider` ховає джерело курсів; клієнт `Money.convert`
не змінюється, коли з'являється `CachedRates` чи справжній API. Це
«ядро» багатьох патернів (Adapter, Strategy, Factory) і принципів
(OCP, DIP) — **найважливіший** принцип GRASP.

## 12.11 GRASP і патерни/SOLID

| GRASP | Реалізують патерни | Споріднений SOLID |
|-------|--------------------|-------------------|
| Information Expert | — (базова евристика) | SRP |
| Creator | Factory, Builder | — |
| Controller | Facade, Command | SRP |
| Low Coupling | Observer, Mediator, DI | DIP |
| High Cohesion | — | SRP, ISP |
| Polymorphism | Strategy, State, Decorator | OCP, LSP |
| Pure Fabrication | Repository, Strategy | SRP |
| Indirection | Adapter, Facade, Mediator, Proxy | DIP |
| Protected Variations | Adapter, Strategy, Factory | OCP, DIP |

Принципи можуть **суперечити**: Expert радить покласти збереження в
`Invoice`, а High Cohesion — ні; тоді виграє Pure Fabrication. Мистецтво
дизайну — у зваженому компромісі, а не в догматичному застосуванні.

## 12.12 Порівняння з іншими мовами

GRASP — мовонезалежний. Відмінності в засобах:

| | Python | JavaScript | C++ |
|---|--------|-----------|-----|
| Creator / Expert | методи класу-власника | те саме | те саме; володіння — `unique_ptr` |
| Low Coupling | duck typing, `Protocol` | duck typing | інтерфейси з `virtual`, шаблони |
| Polymorphism | будь-який метод віртуальний | те саме | `virtual` обов'язковий |
| Protected Variations | `ABC` / `Protocol` | duck typing | абстрактний клас |
| Pure Fabrication | клас-репозиторій | те саме | те саме (+ RAII-обгортки) |

## 12.13 Питання для самоперевірки

1. Яке питання вирішує GRASP і чим він відрізняється від SOLID?
2. Чому метод `total()` має бути в `Order`, а не в `OrderCalculator`?
3. Хто має створювати об'єкти-частини за принципом Creator?
4. Чому контролер не повинен містити бізнес-логіку?
5. Наведіть приклад Pure Fabrication і поясніть, який принцип він рятує.
6. Чим Indirection відрізняється від Protected Variations?
